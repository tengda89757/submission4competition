## 1. 总体方案与架构

**Q1.1 你们整体做了什么？**
- 在 robosuite + MuJoCo 的 Tiago 双臂移动机器人上，完成五个 FactorySorting 场景的「从源站抓取 → 运送 → 放到目标站」。
- 一套代码通吃五关，差异只由 `knowledge/task_config.json` 的参数（场景、源站、目标站、物体）驱动。

**Q1.2 为什么是「统一智能体」而不是每关写一份脚本？**
- 可维护、可解释、防止「过拟合到某一关」。五关共享 `move / pick_up / place_down` 技能；关卡差异是**配置**不是**代码分支**。
- 若被追问：创新点（东墙抓取、A* 膨胀、分散放置）也不是 if-else 硬编码到某关，而是按物体/场景条件触发（如东墙抓取只对 `ROTATED_GRASP_OVERRIDES` 里列出的托盘生效）。

**Q1.3 系统分几层？数据怎么流动？**
1. **感知**：读 SOP（docx）+ 场景语义地图 → 构建 `SceneContext`（源/目标站坐标、物体表）。
2. **规划**：LLM 生成四步计划 `move → pick_up → move → place_down`。
3. **技能**：技能层执行几何/控制（导航 A*、抓取、放置）。
4. **环境**：`RobosuiteBackend` 封装 MuJoCo step、事件记录（grasp_start/end）、轨迹落盘。

**Q1.4 参赛者能改哪些层？**
- 官方规则允许优化**技能层**（skills）。我们的创新都落在 skills / core（`scripted_grasp.py`、`pick_up.py`、`map_loader.py`），**不修改被锁定的环境评测文件**——脚本专家是运行时 monkey-patch 注入（见 Q4）。

## 2. 数据获取（专家高频追问区）

**Q2.1 训练数据从哪来？是人工遥操作吗？**
- **不是遥操作**。数据来自**确定性脚本专家**：一段线性分段的两臂侧向抓取例程，在采集脚本 `load_factory_sorting_1_3fo3erfhisem_collect.py` 里自动跑，把成功回合存成 robomimic HDF5。
- 诚实点：这意味着「示范」本身是程序生成的、可复现的，不带人为抖动。

**Q2.2 采集了多少条？成功率？只存成功回合会不会有偏差？**
- 采集脚本**只保存成功回合**，得到干净示范。
- **若被追问具体条数**：以 HDF5 数据集的 attrs / demo 数为准，现场可打开确认，**不要临场编造数字**。
- 只存成功回合确实带来「幸存者」倾向——这也是 BC 只学会「顺利情形」、在布局变化时不鲁棒的原因之一（见 Q3.4）。

**Q2.3 观测空间是什么？为什么用这些键？**
- `robot0_left/right_eef_pos`、`eef_quat`、`gripper_qpos` + `robot0_robotview_image (128×128)`。
- 双臂末端位姿 + 夹爪开合 + 机器人视角图像，正好覆盖「侧向双臂抓取」需要的状态。

**Q2.4 128×128 分辨率够吗？**
- 对本任务的近距离抓取够用；图像主要提供物体相对位置线索，几何精度由技能层的站位标定与虚拟抓取位保证，不完全依赖像素。

**Q2.5 采集关键常量怎么定的？**（真实代码）
- `control_freq=20Hz`、`up_steps=60`、`xy_steps=120`、`down_steps=80`、`grasp_steps=40`、`safe_z=0.10`、`max_action=0.65`。
- 逻辑：先抬到安全高度（避免扫到桌面）→ 水平接近 → 垂直下探 → 合爪 → 保持。步数是按 20Hz 下动作完成所需时间标定的。

**Q2.6 动作/坐标空间？**
- `OSC_POSE` 末端增量控制（操作空间控制），动作是末端位姿增量而非关节角，`max_action=0.65` 限制单步幅度防抖。

## 3. 模仿学习训练

**Q3.1 用什么算法？为什么是 BC 不是 RL / Diffusion？**
- robomimic 的**纯 MLP 行为克隆（BC）**。
- 选 BC 因为：有确定性专家示范、任务是准静态、要可复现可解释；RL 采样成本高且难复现，Diffusion 对本任务收益不明显。robomimic 里也有 BCQ/CQL/IQL/Diffusion 等实现，我们评估后选了最稳的 BC 基线。

**Q3.2 网络结构 / 超参 / 训练多久 / 硬件？**
- MLP 隐藏层 `(1024, 1024)`，Adam，学习率 `1e-4`，训练 `3000 epochs`。
- **若被追问显卡/时长**：以实际训练环境为准，据实回答，别夸大。

**Q3.3 `model_epoch_150` 和 `model_epoch_500` 什么区别？为什么有两个？**
- `model_epoch_150.pth` 是**官方随赛提供的基线**，在 L1 稳定 10/10。
- `model_epoch_500.pth` 是我们按同流程**重训**的检查点。
- **安装门控**：只有当 `model_epoch_500` 通过 L1 评测才启用，否则**回退 150**——保证不因重训反而变差。

**Q3.4 BC 泛化到 L2–L5 了吗？（这题几乎必问，务必诚实）**
- **诚实回答：没有**。官方 BC（150）过拟合到 L1 布局，在场景 3/5/7/9 即使从标定站位也抓不稳。
- 这不是我们藏着的结论——它**明写在 `scripted_grasp.py` 的文件注释里**，也是我们引入脚本专家兜底的直接动机。
- 所以 L2–L5 的抓取由**确定性脚本专家**完成，BC 主要守住 L1 的已验证路径。

**Q3.5 你怎么判断它「过拟合」？**
- 在 L2–L5 隔离环境跑 BC 抓取，成功率显著掉；而同一套脚本专家原语在 L3/L4 达到 20/20。用**成功率对比**判断，不是看 loss 曲线。

**Q3.6 为什么不多采点数据让 BC 泛化？**
- 时间与算力权衡下的务实选择：脚本专家在技能层即可稳定拿满分，性价比更高。**这是我们承认的局限**，也写进了「未来工作：概率化/学习式抓取减少对脚本依赖」。

## 4. 脚本专家兜底（敏感题：会被问「是否作弊」，要正面接）

**Q4.1 脚本专家是什么？和 BC 什么关系？**
- 就是采集示范用的**同一套线性分段抓取原语**（抬升→接近→下降→稳定→合爪→保持），在评测时直接执行。
- 关系（默认 `fallback` 模式）：**BC 先跑，抓取失败才用脚本专家重新接近**。L1 仍走 BC。

**Q4.2 那全程基本是脚本在抓，BC 还有意义吗？**
- 诚实说：L1 由 BC 完成并守住基线；L2–L5 主要靠脚本专家。BC 的意义是提供 L1 的已验证路径与「先尝试学习策略」的默认行为。
- 我们不夸大 BC，manifest 的 `method_summary` **第一项就是 "Scripted-expert grasp fallback"**，没有包装成「端到端学习」。

**Q4.3 这算不算「写死答案」/ 规避学习？（正面回答）**
- 不算。理由：①**官方 PPT 明确允许优化技能层**；②脚本专家是**通用的几何抓取原语**（对多个托盘、多个场景生效），不是对某一关写死坐标；③导航、放置、评分都走真实物理与官方规则。
- 我们的定位很清楚：**在允许的技能层用确定性方法把「能力」补齐，把每一分的来源讲清楚**，而不是宣称一个其实做不到的学习泛化。

**Q4.4 `fallback / only / off` 三种模式实测差异？**
- 环境变量 `ROBOT_AGENT_SCRIPTED_GRASP`：`fallback`（默认，BC 先跑）/ `only`（仅脚本，调试 L2–L5 更快）/ `off`（仅 BC，用于复现「BC 在 L1 的 10/10」）。
- 隔离验证：脚本专家在 L2 upper 2/2、L5 back 2/2 + center 1/1 + front 1/1、L3/L4 各 20/20。

**Q4.5 monkey-patch 会不会改了被锁定的评测文件？**
- **不会**。后端每次抓取时都会重新 import `run_factory_sorting_grasp_in_wrapped_env`，我们只是在运行时替换该模块属性（`install_scripted_grasp_fallback`），**磁盘上的锁定文件一字未改**；事件记录、抬升、运送附着仍走后端原路径。

## 5. 三大几何创新（细节题，专家最爱抠常量）

**Q5.1 东墙虚拟抓取位：`90°` / `0.315` / `0.11` / `0.941` 这几个数怎么来的？**
- `rot_deg=90`：把抓取几何绕物体中心旋转 90°，让夹爪去夹「朝向机器人的开放面」。
- `forward=0.315`：= 墙半宽 `0.293` + 外插 `0.022`（对应训练时南墙几何 0.215 vs 0.193 的同一规则）。
- `lateral=0.11`：沿被夹墙面的左右夹取点间距。
- `base_dist=0.941`（`TRAINED_BASE_DIST`）：底盘到物体的站位距离，沿用 L1 训练几何，和 `patch_grasp_pose.py` 同一规则。
- 这些不是乱试出来的，是**从场景几何反推**的；隔离环境验证：L2 upper 2/2、L5 back 2/2 + center 1/1 + front 1/1。

**Q5.2 为什么默认抓取 site 不能用？你怎么发现它被碰撞体埋住的？**
- 默认 MuJoCo 抓取 site 落在场景**碰撞代理 AABB 内部**：L2 绿托的西侧 site 被 `production_line_6` 吞到 z=1.9；L5 白托的南侧站位被 `input_1` 桌面挡住。
- 现象是**左臂穿模/抓空**；排查时打印抓取 site 世界坐标并和场景 AABB 比对，发现 site 在障碍内 → 换到开放面用虚拟夹取点。

**Q5.3 分级 A* 膨胀：为什么是 `0.45→0.30→0.15→0.0`？端点为什么要豁免？**
- 根因：底盘能过 1 格窄缝，但**双臂外伸约 0.4 m**，窄缝里会剐蹭模块 → 裁判判碰撞 `−5`。
- 做法：**从最保守 0.45 m 余量开始找无剐蹭路径**，找不到再逐级放宽到 0，保证「有路一定能走、但优先走宽的」。
- 端点豁免：源/目标站台**紧贴**障碍，若对端点也膨胀，approach 格会被「吞掉」→ 吸附后的目标点漂移 → 放置精度下降。所以在起点/目标附近**恢复原始栅格**（`margin_cells+2/+3` 的小块）。

**Q5.4 分散放置：`±0.38` 怎么定的？为什么写在 `pick_up` 里而不是 `place_down`？**
- 值：`lateral = (0.0, 0.38, -0.38)[place_seq % 3]`，归一化保持偏移 `[0.941, lateral]`。
- **为什么在 pick_up**：运送用「附着保持」，抓取瞬间就捕获了 (物体−底盘) 的相对偏移；要改「物体挂在哪」必须在**附着建立时（抓取后）**改，所以逻辑落在 `pick_up._normalize_transport_offset`，不是放置阶段。
- 为什么要分散：L5 三托盘若都丢在同一点，会**链式推挤**把先放的推出 0.80 m 计分半径（实测首托盘偏出 0.92 m）。首个偏移取 0，单物体关卡完全不受影响。
- `0.38` 是让三盘落点在 0.80 m 半径内又互不推挤的经验间距。

**Q5.5 「附着保持」是不是把物体「粘」在机器人上？物理真实吗？（诚实）**
- 诚实说：运送阶段物体通过**环境自带的「运送附着」机制**随底盘移动（保持相对位姿），不是每一步都算接触动力学——这是**赛题环境提供的搬运实现**，我们只调整了它的保持偏移。
- 但被计分的三件事都是真实的：**抓取成功判定**（`grasp_end.success`）、**物体离源位移**、**最终放置位置**。我们没有绕过任何一条评分规则。

## 6. LLM 任务规划

**Q6.1 LLM 到底做什么？**
- 把当前 SOP 行 + 知识库 + 物体地图喂给 LLM，让它输出**固定四步计划** `move → pick_up → move → place_down` 的槽位（去哪、抓什么、放哪）。是**约束式槽位填充**，不是自由发挥。

**Q6.2 既然是固定四步，为什么还要 LLM，规则不就够了？**
- 诚实说：本任务规则化确实能完成，我们也保留了**规则兜底**。LLM 的价值在于**从自然语言 SOP 到结构化计划的解析**与可扩展性（换 SOP 描述不必改代码）。我们不夸大它「会推理」。

**Q6.3 视觉模型用在哪？参与抓取吗？**
- **仅用于读取 SOP docx 文档**（理解任务描述），**不参与抓/放闭环**。抓取靠末端位姿 + 站位标定 + 虚拟抓取位。

**Q6.4 LLM 调用失败/超时怎么办？**
- 走**规则化计划兜底**，返回结构等价的四步计划，执行链路不中断。

**Q6.5 我在 `robosuite_backend.py` 里看到 `qwen3…27b` 的 URL，到底用哪个？（可能被抓包，提前准备）**
- 诚实：那是一个**没清理干净的默认值/历史残留（dead default）**。运行时以 `knowledge/robot_params.json` 的 `ollama_model = qwen2.5:7b` 为准，会覆盖后端硬编码默认。
- 实际生效模型是 **`qwen2.5:7b` via Ollama**。若专家指出，就大方承认是遗留默认值，并说明配置优先级。

## 7. 导航与控制

**Q7.1 A* 跑在什么地图上？分辨率多少？**
- 跑在**场景再生的占据栅格**（`*_scene_regenerated_occupancy_grid.npy`）+ 语义地图（站台/物体坐标）。膨胀余量按分辨率换算成栅格数（`margin_cells = round(margin_m / resolution)`）。

**Q7.2 holonomic 底盘怎么控制？OSC_POSE 是什么？**
- 底盘全向（holonomic），`drive_mode=direct`，`max_linear≈0.70`；手臂用 `OSC_POSE` 操作空间控制（末端位姿增量），`control_freq=20Hz`。

**Q7.3 怎么保证零碰撞？**
- 三重保障：①分级 A* 优先选宽走廊；②站位标定让双臂在抓/放时不撞台；③东墙虚拟抓取位避免左臂穿模。评分里「任意帧碰撞 −5」，我们五关**零碰撞**。

## 8. 评分与可复现（务必讲清「不是自己给自己打分」）

**Q8.1 谁给你打分？你自己写的评分器会不会偏袒？**
- 评分规则来自**平台 `app.py` 的 `SCORE_RULE_VERSION = grasp_success_gate_l5_multi_v2`**。`pipeline/score_trajectory.py` 是它的**无头复刻**，只为离线打分/打包；**平台端用相同规则复核**。
- 评分是**纯几何 + 确定性**：同一条轨迹谁跑都得同一分，无随机、无学习、无可调偏置。

**Q8.2 评分规则具体是什么？`1.0m` / `0.80m` 阈值？**
- 每关满分按 10/15/20/25/30，约 50/50 拆成两项：
  1. **抓取成功且离源**：`grasp_end.success` 且物体在 x 或 y 方向离源站 **> 1.0 m**。
  2. **到达目标**：物体最终 xy 距目标中心 **< 0.80 m**。
- 任意帧碰撞 **−5**。实测五关到位距离 0.09–0.15 m，远小于 0.80 m 阈值。

**Q8.3 `verify_submission.py` 验证了什么？**
- 对五个提交包里的 `trajectory.json` **重新套用官方规则打分**，秒级确认 **100/100**，**无需 GPU/LLM/渲染**。这是给评委的「一键复核」。

**Q8.4 L5 三托盘独立计分怎么算？**
- L5 跟踪 `white_tote_b01_left_center/front/back` 三个白托，**各自**判「抓取且离源(5) + 放到目标(5)」，合计 30。三盘我们都拿满。

**Q8.5 换随机种子 / 重跑还能满分吗？（诚实）**
- **重打分**：完全确定性，任何人对同一轨迹重跑都是 100/100。
- **端到端重跑**：抓取主力是**确定性脚本专家**（无随机），加上站位标定和几何创新，重跑高度可复现；这也是我们敢承诺可复现的原因。若纯 BC 且换种子，L2–L5 不保证——这点我们不隐瞒。

**Q8.6 每关跑一次要多久？为什么 L5 特别久？（真实数据）**
- 端到端运行耗时（本地 headless，含 AI 规划 + 仿真执行，出自各关 `recordings/**/result_*.json` 的 `elapsed_sec`）：L1 **83.9 s**、L2 **77.3 s**、L3 **94.2 s**、L4 **102.3 s**、L5 **453.8 s**，五关合计约 **13.5 分钟**。
- L5 最久是因为它要**完成三趟完整搬运**（三次「移动-抓取-移动-放置」），步数最多；单趟与其它关卡同量级。
- 耗时以**仿真执行**为主；换机器/LLM 服务规划耗时略有差异，但**不影响最终轨迹与得分**（评分只看轨迹）。

## 9. 工程与提交细节（容易被现场打开文件抓到）

**Q9.1 提交包里的队名一致吗？会不会前后对不上？**

## 10. 鲁棒性 / 局限 / 诚实自评

**Q10.1 你们方案最大的局限是什么？**
- 抓取主力是**确定性脚本专家**，不是学习式泛化；BC 只在 L1 稳。静态环境假设、单机器人、依赖地图分辨率。

**Q10.2 换一个你们没见过的新场景，能行吗？**
- 诚实：不保证。脚本专家的站位/几何是按已知场景标定的；新布局需要重新标定或让 BC 泛化。这正是我们「未来工作」的方向。

**Q10.3 你们的创新性体现在哪（对应 40% 创新分）？**
- 三个针对**具体失败模式**的几何方法：东墙虚拟抓取位（解穿模）、分级 A* 膨胀（解双臂剐蹭）、分散放置（解链式推挤掉落）；加上**不改锁定文件的 monkey-patch 兜底**架构。价值是**把每一分的来源讲清楚、并且可复现**。

**Q10.4 如果只能保留一个创新，你留哪个？**
- 留**分级 A* 膨胀**——它跨 L3/L4 通用、直接消除碰撞 −5，收益面最大。（东墙抓取解决的是特定托盘的穿模，分散放置专治 L5。）

**Q10.5 有没有失败的尝试？**
- 有：直接用 BC 抓 L2–L5（失败，促成脚本兜底）；统一 0.3 m 膨胀（仍剐蹭，促成分级阶梯）；同点放置三托盘（首盘被推出 0.92 m，促成分散）。**这些失败恰恰是三个创新的动机**，可以坦诚讲。

## 11. 可能的「陷阱题」与应答策略

**T1 「你们是不是主要靠工程 trick，而不是学习/智能？」**
- 接：是的，我们**务实地承认**抓取主力是确定性方法。但工厂分拣本质是**几何 + 可靠性**问题；我们把有限的学习（L1 BC）与稳定的工程（技能层）**分层组合**，并且**每一分可复现、可核验**。这比宣称一个做不到的端到端泛化更诚实、更工程。

**T2 「满分是不是说明任务太简单？」**
- 接：满分背后是三类真实失败（穿模、碰撞、掉落）被逐一解决；默认方法直接跑是拿不到满分的（BC 出 L1 就掉、统一膨胀会 −5、同点放置会掉盘）。满分体现的是**把已知难点全部闭环**。

**T3 「和纯 BC / 纯经典规划相比，你们优势在哪？」**
- 纯 BC：泛化差、不可解释；纯规划：不吃 SOP 自然语言。我们的**LLM 解析 + 技能层几何 + 确定性兜底**兼顾可读计划与可靠执行，且**一键复现**。

**T4 「评分器是你们自己写的，凭什么信？」**
- 见 Q8.1：规则来自平台 `app.py`，我们只是无头复刻；平台复核同一规则；评分确定性，评委可独立重算。

### 诚实红线（宁可承认，不要硬吹）
1. BC 只在 L1 稳，L2–L5 抓取靠**确定性脚本专家**——如实说。
2. 运送是**环境自带的附着保持**，不是全程接触动力学——如实说。

5. 具体数据条数/训练时长/显卡——**以现场可查为准，不临场编造**。
